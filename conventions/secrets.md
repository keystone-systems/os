# Convention: Secrets (secrets)

How keystone fleets manage secrets: sops-encrypted YAML files committed to the
consumer repo, decrypted per host at activation via sops-nix, declared through
the `keystone.secrets` interface, with recipients derived from the
`keystone.hosts` registry. Ciphertexts live in-repo — there is no separate
secrets repository or flake input.

## Trust model (age recipients)

1. Every secret file MUST be encrypted to age recipients only. Recipients come
   in three kinds:
   - **Hosts** — each host's age recipient is derived from its
     `hostPublicKey` in `hosts.nix` via `ssh-to-age`. The host decrypts at
     activation using `/etc/ssh/ssh_host_ed25519_key`; no per-host age key is
     ever provisioned or backed up.
   - **Humans (admins)** — hardware-backed identities
     (`age1yubikey1...` from age-plugin-yubikey) or the admin user's SSH
     ed25519 key converted via `ssh-to-age`. Admin recipients are listed in
     `secrets/recipients.nix`.
   - **Clusters (future)** — a Kubernetes cluster MAY publish a cluster age
     recipient so that other repos can encrypt manifests to it (see
     "Kubernetes user-app pattern" below).
2. Every secret file MUST include ALL admin recipients — an admin can always
   edit any file. Host recipients are scoped per file (see repo layout).
3. A host MUST only be a recipient of files it consumes. Adding a host to a
   file's recipient list is the authorization act; there is no separate ACL.

## Generated .sops.yaml

4. `.sops.yaml` at the consumer repo root is GENERATED by `ks secrets sync`
   and MUST NOT be edited by hand. Inputs: `hosts.nix` (`hostPublicKey` →
   ssh-to-age) and `secrets/recipients.nix` (admin recipients, plus explicit
   host lists for shared/service/k8s files).
5. `secrets/<host>.yaml` automatically gets that host's recipient — the
   filename stem MUST match a `hosts.nix` entry. Non-per-host files get their
   host lists from `secrets/recipients.nix`.
6. After any recipient change (new host, new admin key, decommissioned
   machine), run `ks secrets sync` then `ks secrets rekey` (rekey runs sync
   first) so every existing ciphertext is re-encrypted to the current set.

## Repo layout and naming

7. Secrets live under `secrets/` in the consumer repo:
   - `secrets/shared.yaml` — secrets consumed by more than one host.
   - `secrets/<host>.yaml` — secrets private to one host.
   - `secrets/services/<x>.yaml` — service-scoped roots of trust shared by
     the hosts running that service (e.g. `services/k3s.yaml` for cluster
     tokens).
   - `secrets/k8s/<cluster>/` — whole-file sops-encrypted Kubernetes Secret
     manifests, applied out-of-band (`ks secrets apply` / repo tooling).
8. The file scopes the secret, so names MUST NOT repeat the scope: no host
   prefixes inside per-host files. The key is `ncrmro-ssh-passphrase`, not
   `ocean-ncrmro-ssh-passphrase` — the fact that it sits in `ocean.yaml` says
   which host it belongs to. Per-user and per-agent prefixes remain
   (`agent-luce-mail-password`), because multiple identities share one file.
9. Ciphertexts are committed. Plaintext MUST never be committed — consumer
   repos MUST carry a pre-commit guard that rejects files under `secrets/`
   lacking sops metadata and any file containing `AGE-SECRET-KEY-`.

## Four secret classes

10. Every secret belongs to exactly one class; the class decides where it
    lives and how it is (re)created:

    | Class | Definition | Storage |
    |---|---|---|
    | **Provided** | An operator obtained it elsewhere (API token, vendor password) and typed it in. | sops file, `keystone.secrets.provided` |
    | **Generated, host-local** | Created on the host, never leaves it (e.g. a machine-local keypair). | Host disk; declared via `keystone.secrets.generated` with `persist = "host"` — currently a STUB that only warns |
    | **Generated, stored** | A root of trust created once and shared by a service's hosts (cluster tokens, signing keys). | Service-scoped sops file (`secrets/services/<x>.yaml`), `persist = "repo"` |
    | **Issued** | Minted on demand from a root of trust, short-lived by design (pre-auth keys, access tokens, mail accounts). | NOT stored in the repo; issued at enrollment time per runbook |

11. Roots of trust (generated-stored) MUST live in service-scoped files so
    their blast radius and recipient list stay minimal.

## Issued credentials

12. Issued credentials MUST have a short TTL and SHOULD be single-use. If an
    issued credential is stored anywhere at rest, it MUST be treated as
    provided-class (encrypted, scoped) — but prefer not storing it at all:
    issue at enrollment, let it expire.
13. The retired anti-pattern: long-lived reusable credentials committed as
    secrets (e.g. 10-year reusable Tailscale/Headscale pre-auth keys in the
    secrets repo). A leaked reusable key enrolls attacker machines for a
    decade. Do not reintroduce this shape.
14. Current runbooks (issue at the root of trust, use immediately):
    - **Headscale pre-auth key**:
      `headscale preauthkeys create --user <user> --expiration 1h` on the
      headscale host. Short expiration, not `--reusable` unless enrolling a
      batch inside the window.
    - **Attic token**: `atticadm make-token --sub <name> --validity <dur>`
      plus the minimal `--pull`/`--push` cache patterns.
    - **Stalwart account**: create the account/app-password via stalwart
      admin API or webadmin; hand the credential straight to its consumer.
15. Operator future — issuance moves into cluster controllers so no human
    handles the credential at all:
    - **Headscale operator**: headscale runs in-cluster; its noise/DERP
      private keys become Kubernetes Secrets and the control URL becomes a
      service identity (`headscale.ncrmro.com`). The operator issues
      ephemeral pre-auth keys at node/agent enrollment (ks.systems/os
      issue #2).
    - **Stalwart mail operator**: stalwart-in-cluster provisions per-agent
      JMAP/mail accounts as Kubernetes Secrets consumed by resident agents
      (e.g. vega).
    - **Attic token controller**: mints scoped, expiring cache tokens for CI
      and hosts.

## Declaration interface (`keystone.secrets`)

16. Consumer repos set `keystone.secrets.dir` (e.g. `./secrets`); all backend
    wiring is gated on it being non-null.
17. Modules and hosts declare consumption via
    `keystone.secrets.provided.<name> = { owner; group; mode; scope; key; }`
    where `scope` is `"host"`, `"shared"`, or `"service:<x>"` and maps to the
    sops file per the repo layout above.
18. Consumers MUST read the runtime path through the accessor —
    `config.keystone.secrets.provided.<name>.path` — never a hardcoded
    `/run/secrets/<name>`. (Home Manager modules without `osConfig` in scope
    are the one tolerated exception.)
19. Modules that take a `*File`/`*Path` option (e.g. `tokenFile`,
    `timeMachinePasswordFile`) keep it as the escape hatch: the option
    accepts any ready-to-read path, and its default (when applicable) is the
    accessor path of a secret the module declares itself.
20. `keystone.secrets.generated.<name> = { persist; generator; }` declares
    generated-class secrets. The backend is not implemented yet — declaring
    one emits a warning and materializes nothing. Declare anyway: the stub is
    the inventory the future backend will fulfill.
21. Existence checks in assertions MUST use
    `config.keystone.secrets.provided ? <name>`, not sops/agenix internals.

## Kubernetes user-app pattern

22. Applications deployed to a cluster from their own repo MUST NOT copy
    their secrets into the fleet config repo. Instead, the cluster publishes
    an age recipient; the app repo sops-encrypts its Kubernetes Secret
    manifests to that recipient and applies them through its own pipeline.
    The fleet repo's `secrets/k8s/<cluster>/` directory is only for
    cluster-infrastructure secrets (e.g. cert-manager's DNS token).

## Golden example

A service root of trust shared by two hosts:

```nix
# hosts/ocean/k3s.nix (and the same declaration on maia)
keystone.secrets.provided.k3s-server-token = {
  scope = "service:k3s";
};

services.k3s.tokenFile =
  config.keystone.secrets.provided.k3s-server-token.path;
```

```nix
# secrets/recipients.nix — who else may decrypt
files."secrets/services/k3s\\.yaml".hosts = [ "ocean" "maia" ];
```

```bash
ks secrets sync                      # regenerate .sops.yaml
ks secrets edit secrets/services/k3s.yaml   # paste the token
ks secrets rekey                     # after any recipient change
```

## Related conventions

- `os.zfs-backup` — the parallel pattern of deriving per-host authority from
  `hostPublicKey` in `keystone.hosts`.
- `process.enable-by-default` — one declaration (`recipients.nix` +
  `hosts.nix`) drives all derived config (`.sops.yaml`, sops-nix wiring).
- `tool.bitwarden` — human-side storage for credentials that exist outside
  the fleet entirely.
